## How to read a spike flow file

Every other epic's flow file describes product behaviour. This one describes **experiments**. The
shape is the same — Given a harness, When the developer runs it, Then a measurement is recorded and
a decision is taken — but the Then clauses assert on _recorded outcomes_, not on shipped features.

That is deliberate, and it is the whole reason this file exists. The roadmap's rule for M0 is that
**a spike is done when it has produced either a working command you can re-run, or a written reason
why the plan changes; a spike that ends in "seems fine" has not run.** Writing the assertion before
running the agent is what stops a spike from becoming a story told afterwards. A scenario here
"passes" when its question is answered and the answer is written down — including when the answer
is "the fallback is taken".

## Actors

| Actor                  | Description                                                                                                                                     |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Developer**          | The author, running spikes on their own laptop under their own OS account                                                                       |
| **Spike harness**      | A throwaway script under `spikes/<id>/`, outside the workspace globs                                                                            |
| **Provider agent**     | A real vendor CLI subprocess reached over ACP — `@agentclientprotocol/claude-agent-acp@0.64.1` (adapter path) or `gemini --acp` 0.53.1 (native) |
| **Decision note**      | `docs/spikes/S<n>-<slug>.md` — question, timebox, what ran, measurement, decision, fallback, closed risk id                                     |
| **Capability fixture** | `fixtures/capabilities/<agent>@<version>.json`, generated by the probe, never hand-written                                                      |
| **Board**              | `docs/delivery/board.md`, whose EPIC-01 row is gated on the go/no-go                                                                            |

## Preconditions common to all flows

```gherkin
Background:
  Given Node 24 and Node 26 are both installed and selectable
  And pnpm 11.18.0 is installed via "npm i -g pnpm@11" and NOT via "corepack enable"
  And git >= 2.38 is on PATH
  And the repository contains a "spikes/" directory that is excluded from pnpm-workspace.yaml's packages globs
  And "docs/spikes/TEMPLATE.md" defines the decision-note shape with required "## Measurement" and "## Decision" sections
  And no production package under "packages/" has been created yet
```

Two preconditions apply only to KAR-00.1's scenarios and are stated in that scenario's own
Background: the vendor CLIs are installed and authenticated **by the developer, under their own
account**, and the harness reads no token file, sets no auth environment variable and transmits no
credential anywhere (AR-1).

## EPIC-00-S1 — Zero-build import across a pnpm workspace symlink, on both Node majors

**Verifies:** KAR-00.2 · **Type:** Happy path · **Automated at:** integration

```gherkin
Feature: The dev loop runs TypeScript source across package boundaries with no build step

  Background:
    Given a throwaway workspace at "spikes/s2-zero-build/" with packages "a" and "b"
    And package "b" declares "exports": { ".": "./src/index.ts" }
    And package "b" declares a publishConfig exports override pointing at "./dist/index.js"
    And package "a" depends on "@spike/b" with the "workspace:*" protocol
    And "pnpm install" has linked "@spike/b" as a symlink inside "a/node_modules/@spike/"
    And every source file uses only erasableSyntaxOnly-legal syntax

  Scenario Outline: node runs the source directly through the workspace symlink
    Given the active Node major is <node>
    When the developer runs "node a/src/main.ts"
    Then the process exits with code 0
    And stdout contains "hello from @spike/b"
    And no build artefact exists at "b/dist/"
    And the decision note records "<node>: pass"

    Examples:
      | node |
      | 24   |
      | 26   |

  Scenario: the other three tools resolve the same way
    When the developer runs "pnpm vitest run" inside package "a"
    And the developer runs "pnpm tsc -b"
    And the developer runs "pnpm vite build" against a scratch entry importing "@spike/b"
    Then all three exit with code 0
    And none of them reports an unresolved import for "@spike/b"
    And the decision note's "## Decision" section reads "adopt node --watch; no tsx required"

  Scenario: the publishConfig swap produces a tarball that points at dist
    When the developer runs "pnpm pack" inside package "b"
    And unpacks the resulting tarball
    Then the packed package.json "exports" resolves "." to "./dist/index.js"
    And it does not resolve "." to "./src/index.ts"
```

**Notes:** This is the load-bearing assumption in the whole dev story (A2-1, graded **High**), and
it must be the first spike run because it decides how every other spike is written. The reason it
should work is that Node resolves the symlink realpath before applying its "no TypeScript inside
`node_modules`" rule — but that chain was reasoned about, never executed. The `pnpm pack` scenario
is not decoration: `@DeFlow/*` are never published, so the `publishConfig` block is belt-and-braces
that only fails visibly the day someone actually packs one.

## EPIC-00-S2 — Type stripping is refused inside `node_modules` and the `tsx` fallback is adopted

**Verifies:** KAR-00.2 · **Type:** Failure · **Automated at:** _not automated — precondition did
not hold; see Outcome below_

> **Outcome (2026-08-04): not applicable.** This scenario's Given is "`node a/src/main.ts` failed to
> strip types". It did not fail — EPIC-00-S1 passed on both Node majors, so the whole fallback
> branch below (adopt `tsx@4.23.4`, change KAR-01.3 acceptance criteria 2 and 5, lose `node --watch`
> crash-resume, re-measure KAR-01.6's pre-push budget) never became reachable, and **none of its
> Then clauses are automated**. `tsx@4.23.4` is not a dependency of this repo and must not be added
> to make a scenario pass whose Given never happened.
>
> What was automated instead is the counterfactual, in the same file
> (`test/integration/spike-s2-zero-build.test.ts`, suite _"EPIC-00-S2 — the node_modules
> type-stripping refusal is real, and the symlink is what avoids it"_): with the single variable
> flipped — `@spike/b` materialised as a real directory under `a/node_modules/@spike/` rather than
> a pnpm symlink — `node` does fail with `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING` on both
> majors, while the symlinked layout still exits 0. That proves the refusal this scenario predicted
> is real and that the workspace symlink is precisely what avoids it, which is the strongest claim
> available once the happy path wins. It also makes pnpm's symlinked node-linker load-bearing: if
> the layout ever changes, that test goes red first and the scenario below becomes live again.
>
> The scenario text is kept, unedited, because it is the written form of the fallback plan. See
> [docs/spikes/S2-zero-build.md](../../spikes/S2-zero-build.md).

```gherkin
Feature: The dev loop has a stated fallback that is taken deliberately

  Scenario: Node refuses to strip types resolved through the workspace link
    Given the spike workspace from EPIC-00-S1
    When the developer runs "node a/src/main.ts"
    Then the process exits with a non-zero code
    And stderr contains the error code "ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING"
    And the decision note's "## Measurement" section records the exact stderr

  Scenario: the fallback is taken and its blast radius is named before EPIC-01 starts
    Given "node a/src/main.ts" failed to strip types
    When the developer re-runs the same entry with "tsx@4.23.4"
    Then the process exits with code 0 and prints "hello from @spike/b"
    And the decision note's "## Decision" section reads "adopt tsx@4.23.4 watch"
    And the note names KAR-01.3 acceptance criteria 2 and 5 as changed
    And the note records that "node --watch" is no longer the free crash-resume test described in 03-local-development.md §5
    And the note records that KAR-01.6's pre-push budget must be re-measured under tsx
```

**Notes:** The important behaviour here is not the failure — it is that the failure produces a
_named list of downstream story changes_ rather than a shrug. The escape hatch is documented in
[03-local-development.md §5](../../03-local-development.md), but the doc also says "confirm the
problem before reaching for it", which is exactly what this scenario does. Losing `node --watch`
costs more than an inconvenience: the restart-on-save behaviour is described as free, continuous,
adversarial testing of F4.2, and if it goes, EPIC-03 and EPIC-06 lose an everyday safety net.

## EPIC-00-S3 — Non-erasable syntax in a linked package fails at runtime

**Verifies:** KAR-00.2 · **Type:** Edge case · **Automated at:** integration

```gherkin
Feature: erasableSyntaxOnly is permanent because there is no transform flag left

  Scenario Outline: banned syntax is rejected by the runtime, not merely by the compiler
    Given package "b" is temporarily modified to contain <syntax>
    When the developer runs "node a/src/main.ts" on Node 26
    Then the process exits with a non-zero code
    And stderr names an unsupported TypeScript syntax error
    And the decision note records that "--experimental-transform-types" was removed in Node 26.0.0 and no escape hatch remains

    Examples:
      | syntax                                        |
      | "enum Status { Ok, Fail }"                    |
      | "namespace X { export const y = 1 }"          |
      | "constructor(private readonly db: Db) {}"     |

  Scenario: the replacement idiom runs
    Given package "b" uses "const Status = { Ok: 'ok', Fail: 'fail' } as const" with a derived union type
    When the developer runs "node a/src/main.ts"
    Then the process exits with code 0
```

**Notes:** This scenario exists to make D4 concrete before 5,000 lines are written. The three
Examples rows are the three that a TypeScript developer reaches for by reflex. Note the asymmetry
worth recording in the note: `tsc` reports these at compile time with `erasableSyntaxOnly: true`,
but `node` rejects them at _runtime_, and in a zero-build dev loop the runtime is what the developer
meets first.

## EPIC-00-S4 — Full ACP prompt cycle against a real adapter

**Verifies:** KAR-00.1 · **Type:** Happy path · **Automated at:** integration

```gherkin
Feature: DeFlow can act as an ACP client against a real vendor agent

  Background:
    Given "@agentclientprotocol/claude-agent-acp@0.64.1" is installed and authenticated under the developer's own account
    And the harness reads no token file and sets no auth environment variable
    And the harness tees raw stdin and stdout bytes to "recordings/claude-agent-acp@0.64.1/full-cycle.ndjson" at the transport level, before any parsing
    And an ajv validator is loaded with "@agentclientprotocol/sdk/schema/schema.json"

  Scenario: the six steps complete and the capability fixture is generated
    When the developer runs "node spikes/s1-acp/run.ts --agent claude-agent-acp"
    Then the "initialize" response reports protocolVersion 1
    And the response's agentCapabilities block is written verbatim to "fixtures/capabilities/claude-agent-acp@0.64.1.json"
    And "session/new" returns a session id
    And DeFlow's stdio MCP server was accepted in the "mcpServers" argument without error
    And "session/prompt" is accepted
    And at least three "session/update" notifications were received
    And the client sent a "reject_once" outcome to a "session/request_permission" request
    And the agent did not perform the rejected action
    And "session/cancel" produced a prompt response with stopReason "cancelled"
    And at least one trailing "session/update" was accepted after the cancellation without the read loop wedging
    And every recorded frame validated against the ACP schema's 262 $defs
    And the decision note records "A0-1: closed"
```

**Notes:** This is the single riskiest unverified assumption in the project (A0-1, **Critical**),
and the kill criterion attaches here. The research verified `initialize` live against all five ACP
entry points on 2026-08-02 and confirmed all five negotiate wire `protocolVersion: 1` — everything
past that step is spec-read, not observed. Two details in the Then clauses are not incidental. The
trailing-`session/update`-after-cancel clause is the specific deadlock the kill criterion names.
And the schema validation is nearly free: there is **no official ACP conformance kit** — verified
negative, and web search confidently asserts otherwise by conflating it with an unrelated academic
protocol also abbreviated ACP — so the shipped `schema.json` plus `ajv` (already transitively
present via the MCP SDK) is the only conformance signal available.

## EPIC-00-S5 — The same cycle across both agents, with an uneven capability matrix

**Verifies:** KAR-00.1 · **Type:** Edge case · **Automated at:** integration

> **Outcome (2026-08-04):** both fixtures are generated and both rows match the Examples table —
> `claude-agent-acp@0.64.1` advertises `session.resume` and `session.list`, `gemini-cli@0.53.1`
> advertises neither. `gemini --acp` completed only `initialize`: `session/new` returned
> `-32000 Gemini API key is missing or not configured.`, and AR-1 forbids the harness from setting
> one, so its remaining five steps are recorded as blocked for a credentials reason rather than a
> protocol one. Scenario 2's Given (a probed value contradicting the snapshot) did not occur with
> either vendor, so it is automated against the `fake-divergent` agent binary instead, which
> advertises `session.resume` where its own snapshot row denies it — the harness writes the
> observed value and reports the divergence rather than falling back.

```gherkin
Feature: The capability matrix is generated per agent, never assumed

  Scenario Outline: probe each agent and record what it actually advertises
    Given <agent> is installed at <version> and authenticated
    When the developer runs "node spikes/s1-acp/run.ts --agent <agent>"
    Then a fixture is written to "fixtures/capabilities/<agent>@<version>.json"
    And the fixture's "session.resume" field is <resume>
    And the fixture's "list" field is <list>
    And the decision note records which of the six cycle steps completed for this agent

    Examples:
      | agent              | version | resume | list  |
      | claude-agent-acp   | 0.64.1  | yes    | yes   |
      | gemini-cli         | 0.53.1  | no     | no    |

  Scenario: a probed value that contradicts the 2026-08-02 snapshot is treated as news, not as an error
    Given the 2026-08-02 snapshot recorded "gemini --acp 0.53.1: session.resume = no"
    When the probe reports "session.resume = yes" for the installed version
    Then the harness writes the observed value to the fixture
    And it does not fall back to the snapshot
    And the decision note flags the divergence and the installed version string
```

**Notes:** The capability matrix is genuinely uneven — measured live on 2026-08-02, two of five
agents cannot resume at all (`copilot --acp` 1.0.77 and `gemini --acp` 0.53.1), and `codex-acp`
1.1.9 reports `mcp.acp: false` while others simply omit it. The second scenario encodes the rule
that matters more than any single value: **the snapshot is a test fixture, never a constant**
(A0-9). Two of the five versions probed were published the same day they were probed. Anything that
hardcodes this matrix is wrong within a month, and EPIC-05's KAR-05.2 depends on this being
established in week one.

## EPIC-00-S6 — Streaming is incremental, measured by client-side receipt timestamps

**Verifies:** KAR-00.1 · **Type:** Edge case · **Automated at:** integration

> **Outcome (2026-08-04): scenario 1 passes; scenario 2 is not applicable.** 17 `session/update`
> notifications arrived from `claude-agent-acp@0.64.1` with a client-side receipt spread of
> **6699 ms** against the 500 ms threshold, and the full inter-arrival list is in
> [the decision note](../../spikes/S1-acp-round-trip.md#streaming-is-incremental-ac4-epic-00-s6).
> Scenario 2's Given ("all frames were received within 50 ms of the prompt response") did not
> occur, so its Thens — record "streaming is not incremental", name F10.1/F10.6 as affected, carry
> A0-2 into KAR-00.7 as kill-criterion input — are **not automated**.

```gherkin
Feature: session/update notifications arrive as they happen, not in a burst at turn end

  Scenario: incremental arrival is proven by measurement
    Given the harness records a monotonic receivedAt for every inbound frame
    When a prompt is sent that is expected to produce a multi-part response
    Then at least three "session/update" notifications are recorded
    And the spread between the first and last receivedAt exceeds 500 ms
    And the decision note's "## Measurement" section contains the full inter-arrival list

  Scenario: a burst at turn end is recorded as a finding, not smoothed over
    Given all "session/update" frames were received within 50 ms of the prompt response
    Then the decision note records "streaming is not incremental on this adapter"
    And the note names F10.1 and F10.6 as affected
    And the note names A0-2 (community adapter fidelity) as the suspected cause
    And the finding is carried into KAR-00.7 as kill-criterion input
```

**Notes:** "At least three streamed notifications arrive incrementally, not in one burst at the
end" is the roadmap's own success criterion for this step, and the 500 ms threshold is what turns
it from an impression into an assertion. The whole live-graph and live-stream product surface
assumes this. If the adapter buffers, the correct conclusion is not "the UI will be a bit laggy" —
it is that the ACP path loses its main advantage over the shim path and KAR-00.7 re-weights.

## EPIC-00-S7 — ACP surfaces no token usage, so `tokenAccounting` degrades honestly

**Verifies:** KAR-00.1 · **Type:** Failure · **Automated at:** integration (scenario 2); scenario 1
**not applicable** — precondition did not hold, see Outcome below

> **Outcome (2026-08-04): scenario 1's premise is false, and that is the finding.** Its Given is
> "the developer greps the frame log … Then no such field is found". Such fields were found, in
> quantity: every `session/prompt` response carries
> `usage: { inputTokens, outputTokens, cachedReadTokens, cachedWriteTokens, totalTokens }`, eight
> `usage_update` notifications carried `{ used, size }` against a 1,000,000-token context window,
> and two of them carried `cost: { amount, currency }`. `Usage` and `UsageUpdate` are `$defs` of
> the protocol, not a vendor extension. So the manifest value for this adapter is
> `tokenAccounting: 'exact'`, **not** the `'estimated'` fallback this scenario prescribes, and
> F9.1 does not degrade on the ACP path. Those Then clauses are **not automated**; the positive is
> asserted in their place (`test/integration/spike-s1-acp.test.ts`, suite _"EPIC-00-S7"_).
>
> Two halves of the scenario did hold and are automated: **compaction state is genuinely absent**
> (no frame carries a field named for it, and `compact` appears in none of the 262 `$defs` — it
> occurs in the log only as the name of a slash command, which is why the assertion is written
> against key positions rather than as a substring grep), and **`structured_output` is absent from
> the protocol entirely**, so F6.9 needs DeFlow's own bounded repair loop and KAR-09.9 owns it.
> The honest-degradation requirement is unchanged and still asserted: a missing value renders as
> unknown, never as `0`.

```gherkin
Feature: The cost of the ACP-first path is known before it is paid

  Scenario: the frame log contains no usage or compaction information
    Given the complete recorded frame log for a full prompt cycle
    When the developer greps it for any token, usage, cost or compaction-shaped field
    Then no such field is found
    And the decision note records "A0-3: ACP surfaces no token accounting"
    And the note records that F9.1 (live cost accounting) and F10.5 (context budget visualisation) degrade on this path
    And the note prescribes "tokenAccounting: 'estimated'" as the manifest value for ACP adapters
    And the note records that the UI must render the missing value as unknown rather than as zero

  Scenario: structured_output is absent from a successful result
    When the developer inspects the result envelope of a successful prompt
    Then no populated "structured_output" field is present
    And the decision note records "A4-2: unconfirmed → confirmed absent"
    And the note records that F6.9's handoff-contract validation cannot lean on the vendor and needs DeFlow's own bounded repair loop
    And EPIC-09's KAR-09.9 is named as the affected story
```

**Notes:** Both halves of this scenario are questions the roadmap explicitly says to answer "while
the harness is warm", because re-authenticating and re-spending quota later is expensive. The
honest-degradation requirement is the point: a UI that renders an unknown token count as `0` is
worse than one that renders it as unknown, because a zero looks like a measurement. Note the
related finding this scenario should cross-check against: Claude Code 2.1.220 contains **zero
occurrences of the string `gen_ai.`** and emits a private `claude_code.*` namespace instead, so
telemetry is not a back door to the same numbers.

## EPIC-00-S8 — A 10 MB frame with no newline grows `LineBuffer` without bound

**Verifies:** KAR-00.1 · **Type:** Failure · **Automated at:** integration

```gherkin
Feature: The client imposes its own frame cap because the SDK does not

  Scenario: an agent that never emits a newline is not allowed to OOM the daemon
    Given the harness's transport is fed a 10 MB payload containing no "\n"
    When the client reads from the stream
    Then the harness's own frame cap fires before the buffer exceeds the cap
    And the connection is terminated with a typed framing failure
    And the process does not exceed its heap limit
    And the decision note records the cap value chosen and the reason

  Scenario: the cap value is carried forward as a named constant for EPIC-05
    Then the decision note names KAR-05.4 (frame-size guard, backpressure and blob spilling) as the consumer of this value
```

**Notes:** A verified footgun: `@agentclientprotocol/sdk@1.3.0`'s `LineBuffer` has **no maximum
line length**, so an agent that never emits `\n` will grow it until the daemon dies. The
architecture's answer is an 8 MiB frame cap, and this spike is where that number is chosen against
a real payload rather than picked. The mock agent's scenario 8 (a single 10 MB line) exists in
EPIC-04 specifically so this path can be regression-tested forever after without a vendor CLI.

## EPIC-00-S10 — Cancellation deadlocks, and the kill-criterion input is recorded

**Verifies:** KAR-00.1, KAR-00.7 · **Type:** Failure · **Automated at:** integration (against
fake-agent binaries — see Outcome below)

> **Outcome (2026-08-04): none of the three Givens occurred against a real agent.**
> `session/cancel` produced `stopReason: 'cancelled'` **6 ms** later from
> `claude-agent-acp@0.64.1`, one trailing `session/update` was flushed afterwards and accepted, and
> a subsequent `session/new` round-tripped — so the transport had not wedged. Scenario 3's Given

## EPIC-00-S13 — A page reload sends no `Last-Event-ID`, so `?since=` is mandatory

**Verifies:** KAR-00.3 · **Type:** Edge case · **Automated at:** e2e (real Chromium) and unit

> **Outcome (2026-08-04): all four scenarios hold, and the third one added a clause.** Verified
> against Chromium 151 by `e2e/spike-s4-one-port.test.ts`. A fresh `EventSource` after a reload
> really does send no `Last-Event-ID`, and an automatic reconnect really does send one.
>
> What the reconnect *also* does is re-request the **same URL** — so a page that hydrated at
> `/api/stream?since=137` and lost its connection at seq 150 sends the stale `?since=137` and a
> current `Last-Event-ID: 150` together. A server that prefers `?since` in that case replays
> thirteen events the page already had, which is the duplication this scenario forbids. The contract
> is therefore **resume from the greater of the two cursors** (a tie counts as a reconnect), pinned
> by `test/spike-s4-resume.test.ts`. KAR-15.3 inherits it.

```gherkin
Feature: Stream resume works across a page reload, not only across an automatic reconnect

  Scenario: the browser omits Last-Event-ID on a fresh EventSource
    Given the client has consumed events up to seq 137
    When the page is reloaded and a new EventSource is constructed
    Then the server observes no "Last-Event-ID" request header
    And the decision note records this as verified browser behaviour, not a bug

  Scenario: explicit hydration closes the gap
    Given the client persisted its last seen seq of 137
    When the client first requests the events endpoint with "?since=137"
    And then opens the stream
    Then every event with seq greater than 137 is delivered exactly once
    And no event is delivered twice
    And no event is lost

  Scenario: an automatic reconnect does send Last-Event-ID
    Given the connection is severed by the network rather than by a reload
    When the browser reconnects automatically
    Then the request carries a "Last-Event-ID" header
    And the server resumes from strictly greater than that id

  Scenario: a gap in the sequence is expected and is not an error
    Given a previous transaction rolled back and burned an AUTOINCREMENT value
    When the client receives seq 140 immediately after seq 138
    Then the client does not report a missing event
    And the contract is "resume from strictly greater than seq", never "expect seq + 1"
```

**Notes:** `EventSource` sends `Last-Event-ID` **only on automatic reconnect**, never on a fresh
`new EventSource()` after a page reload, and it cannot set custom headers at all — **verified
2026-08-02**. That single fact is why the API needs both resume mechanisms, and why
[03-local-development.md §13](../../03-local-development.md) lists "UI shows nothing after a reload
following a daemon restart" as a troubleshooting row with "this path is mandatory, not an
optimisation" attached. The sequence-gap scenario is included here because it is the same contract
seen from the other end, and because rolled-back transactions genuinely burn `AUTOINCREMENT` values
in the real ledger.

configurations, then all four again, **five rounds**, at **50,000 events** so the shortest window is
about **63 ms**. Each round yields its own ratios from numbers taken seconds apart, and the median
across rounds decides. Measured 2026-08-06 on an 8-core macOS box, `batchingGainNormal` by median:
**6.59** idle, **5.23** and **6.21** under twelve CPU hogs, **7.18** beside a live integration slice —
where the old single sweep, measured in the same minute beside that slice, gave **2.02**. Verified
red on the regressions: batching that no longer batches (one commit per transaction) gave per-round
gains of 0.85–1.07 and failed; the FULL/NORMAL relationship inverted gave per-round penalties of
0.07–0.19 and failed both halves.

The `fullfsync = 1` half of the FULL-costs-more claim stays on the recorded sweep, and the reason is
measured: there FULL manages **335** ev/s against NORMAL's **48,143**, a separation of **143x**
against the ff0 pair's **3.3x**. Two orders of magnitude do not invert because a box is busy, and the
event count that gives the ff0 quartet honest windows would make an ff1 round take minutes.

**Notes:** Every fsync-sensitive number in
[05-durable-execution.md](../../05-durable-execution.md) was measured on Linux, likely on
overlayfs. macOS uses `F_FULLFSYNC` and is typically **slower** for fsync (A1-1). The relative
shape should hold, but the absolute numbers decide whether `FULL` is affordable, and that is a
product trade-off — it is the difference between "a crash may lose the last few events" and "every
append waits on the disk" — not a tuning detail to be defaulted.

## EPIC-00-S19 — The pty install matrix, cell by cell, with a no-TTY fallback

**Verifies:** KAR-00.5 · **Type:** Edge case · **Automated at:** integration (five real cells: two
Node majors on the host, three containers)

> **Outcome (2026-08-04): three cells pass, two fail, and both fallbacks are taken rather than
> noted.** Everything installs everywhere with zero compilation; what separates the cells is whether
> the installed binary then loads. Pass: `macos-arm64-node24` and `macos-arm64-node26` (`/dev/ttys002`,
> echoes) and `linux-glibc-node26` (`node:26-slim`, glibc 2.41, `/dev/pts/0`). Fail:
> **`linux-glibc-node24`** — `node:24-slim` is Debian bookworm, glibc **2.36**, and
> better-sqlite3's `linux-arm64` prebuild wants `GLIBC_2.38`; a control cell on
> `node:24-trixie-slim` (same Node major, glibc 2.41) loads it fine, so the variable is the
> distribution, and the fallback is a **documented prerequisite of glibc ≥ 2.38**. And
> **`linux-musl-node24`** — `@lydell/node-pty` ships no musl build, npm installs the glibc
> `linux-arm64` one anyway, and `dlopen` fails on the missing `ld-linux-aarch64.so.1` (the package's
> own error says "Cannot find module", which is misleading); the fallback is **no-TTY**, and
> better-sqlite3 itself loads there from `linuxmusl-arm64.node`. Upstream `node-pty@1.1.0` failed in
> all three Linux cells with `node-gyp` actually running, and **succeeded** on darwin — it ships
> darwin and win32 prebuilds and no Linux ones — which is exactly why its `||` fallback is
> dangerous: the platform the maintainer tests on is the platform where it works. **x64 was not
> tested here**; every container is `linux/arm64` because the docker host is Apple Silicon.

```gherkin
Feature: The last native-install risk for "npx DeFlow up" is bounded

  Scenario Outline: install and allocate a pty with no compiler present
    Given a box running <platform> with Node <node> and no compiler on PATH
    When the developer installs "@lydell/node-pty@1.2.0-beta.14"
    And spawns a pty
    Then the install completes with zero compilation
    And a /dev/pts device is allocated and echoes input
    And the matrix cell is recorded as "pass" in the decision note

    Examples:
      | platform              | node |
      | macOS Apple Silicon   | 24   |
      | macOS Apple Silicon   | 26   |
      | Linux glibc           | 24   |
      | Linux glibc           | 26   |
      | Linux musl            | 24   |

  Scenario: a failing cell becomes a documented fallback, never a shrug
    Given a matrix cell failed to install or allocate
    Then the decision note records it as either a documented prerequisite or a no-TTY fallback path
    And the note records that no agent process needs a TTY, because ACP and every headless mode are pure pipe protocols verified across five agents
    And the note records that a pty is needed only for DeFlow's own ACP "terminal/*" implementation
    And the fallback is to not advertise terminal capability on that platform

  Scenario: upstream node-pty is confirmed unusable and the reason is recorded
    Given "node-pty@1.1.0" is installed in the same compiler-less environment
    Then the install fails
    And the note records that its install script is "node scripts/prebuild.js || node-gyp rebuild" and silently falls back to compiling
```

**Notes:** This is the single remaining native-install risk for `npx DeFlow up` (NF6, A0-6), and

`1.2.0-beta.14`, a beta of a community fork, and it is the only native dependency in the published
package, so [roadmap §5](../../17-roadmap.md) puts a monthly re-check on it reaching stable.
